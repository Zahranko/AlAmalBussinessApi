# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Build and run (from repo root, where `AlAmalBusiness.sln` lives):
```
dotnet build
dotnet run --project AlAmalBusiness.Api
```

EF Core migrations (always pass both flags — `AppDbContext` lives in Infrastructure, `Program.cs`/config lives in Api):
```
dotnet ef migrations add <Name> --project AlAmalBusiness.Infrastructure --startup-project AlAmalBusiness.Api
dotnet ef database update --project AlAmalBusiness.Infrastructure --startup-project AlAmalBusiness.Api
```

There is no test project in this solution yet.

Dev DB: SQL Server at `localhost\MSSQLSERVER01`, database `AlAmalBusiness` (see `AlAmalBusiness.Api/appsettings.json`). Swagger UI is available at `/swagger` in the Development environment.

## Architecture

Four-project layered/clean architecture, referenced in one direction: `Api → Application/Infrastructure → Domain`. `Infrastructure` and `Application` do not reference each other directly — `Api`'s `Program.cs` is the composition root wiring `I<X>Repo` (Infrastructure) and `I<X>Service` (Application) into DI.

- **Domain** — entity models (`Models/`), repository interfaces (`IRepositories/`), enums (`Constants/`). No EF, no business logic.
- **Application** — DTOs (`DTOs/`) and business logic (`Services/Interface/`, `Services/Imp/`). Services depend only on repository *interfaces* from Domain, never on Infrastructure directly.
- **Infrastructure** — `AppDbContext` (EF Core + ASP.NET Identity), repository implementations (`Repository/Imp/`), migrations, `Seeding/DbInitializer` (seeds `AppRoles` on startup).
- **Api** — controllers, `Program.cs` (all middleware/DI wiring), SignalR hubs.

Every feature follows **Controller → Service → Repository → `AppDbContext`/EF model**, with DTOs per feature under `Application/DTOs/<Feature>/`. `DepartmentRepo`/`DepartmentService`/`DepartmentController` is the reference template for a plain lookup-list CRUD feature: repo does raw EF + an `IsXExist(name, excludeId)` uniqueness check, service returns a `{Success, Message, Data}` response DTO, no separate PATCH-status endpoint (`IsActive` travels in the same Create/Update DTO). **Every lookup DTO must include `Id`** — `DoctorDTO`/`ProcedureDTO`/`ReferalSourceDTO`/`ClosedReasonDTO` shipped without it initially (found 2026-08-31 wiring the frontend: a client has no way to reference an entity it can't get the id for), now fixed.

**Time: every business timestamp is Jordan time (UTC+3) from `Domain/Constants/AppClock` — never `DateTime.Now`/`Today`/`UtcNow` (added 2026-09-14).** Production's web and SQL servers run on Central European time, so `DateTime.Now` was 1-2h behind Amman and `UtcNow` 3h behind, and the console displays stored values as-is (no offset in the JSON). `AppClock` is a fixed +3 offset on purpose (Jordan has had no DST since 2022; an unpatched Windows `Jordan Standard Time` rule would still apply +2 in winter). Only auth internals (JWT expiry, `RefreshToken` timestamps) stay on `UtcNow`. Existing rows were shifted the same day: CRMS imports (Leads.Id <= 1126, LeadHistories.Id <= 3854) had been UTC (+3h), native `Now` columns CEST (+1h), native `UtcNow` columns (+3h); user-picked dates untouched; originals kept in `ZZ_TimeFix_Backup_20260914`. The SQL server's own time zone is irrelevant — nothing uses `GETDATE()`, and a shared host can't change it anyway.

Enums serialize as their string name everywhere (`"Cash"`, `"Pending"`), not the numeric value — `Program.cs`'s `AddControllers().AddJsonOptions(...)` registers a global `JsonStringEnumConverter`. Don't remove this; without it every enum-typed request/response field silently becomes a bare number and any client sending/expecting a string name gets a 400 or garbage data.

### CRM / Lead feature

Lives under `Area/CRM/` in Api (`Area/CRM/Controllers/`, `Area/CRM/Hubs/`) and `DTOs/CRM/` in Application (`DTOs/CRM/Lead/`, `DTOs/CRM/LeadManageList/` for Doctors/Procedures/ReferralSources/ClosedReasons, `DTOs/CRM/Stats/`). This was ported from a separate legacy CRM app (`CRMS`) with two deliberate behavior changes from that original:

- **No "Forward" workflow** — a lead's owner only changes via Claim, never transferred to another user.
- **No separate "Failed" status** — `LeadStatus` is `New, Pending, Waiting, Success, Closed`. Closing a lead requires picking a `ClosedReason` (what the old app called `FailureReason`), enforced in `LeadService.FollowUpAsync`.

`Lead.CreatedById`/`ClaimedById` are `string` FKs straight to the local `AspNetUsers` table (via `IdentityUser`-derived `User`) — display names are read through EF navigation (`lead.CreatedBy.UserName`), no username-snapshot columns. Every workflow action (`Created`, `Claimed`, `ReOpened`, `Edited`, `FollowUp`) is appended to `LeadHistory` as an audit timeline, read back via `ILeadHistoryRepo`.

`LeadHub` (`/hubs/leads`) is a plain SignalR broadcast — `LeadCreated`/`LeadStatusChanged` events go to every connected client, and only CRM roles may connect (`[Authorize(Roles = CrmRoles.Access)]`, 2026-09-15 — `LeadCreated` carries patient name and phone; the `Active*` lookup endpoints use the same gate), no persisted notification inbox, no per-user targeting. `ILeadNotifier` is the Application-side abstraction (implemented in Api as `SignalRLeadNotifier`) so Application stays free of a SignalR package reference; notifier calls are always best-effort (wrapped so a push failure never fails the underlying write).

`Lead.CreatedDate` defaults to `AppClock.Now` (Jordan time, not UTC) — `LeadRepo`'s date-range filters compare against Jordan day boundaries accordingly. Don't introduce UTC-conversion logic there without changing the model default too.

`Lead.PhoneNum` is `string?` (not `int?` — was fixed 2026-08-31, storing as int silently drops a leading `0`, which every Jordanian mobile number starts with). Lead search (`LeadRepo.PageLeadsAsync`) matches `Name`/`NickName`/`PhoneNum`, and is leading-zero-tolerant on phone (matches whether the searcher types the `0` or not). Since 2026-09-15 a term made only of digits and phone punctuation is tried against `PhoneNum` alone and any other term against `Name`/`NickName` alone (feedback search splits the same way, always including `ReferenceNumber`).

**Performance shape (found 2026-09-05, production = SmarterASP 1 GB shared pool + a separate shared SQL box, so every query is a network round trip):** list endpoints project straight into `Domain/IRepositories/CRM/LeadListRow` (`LeadRepo.ToRow`) — never `Include` six entities for a list row again (that pulled both `AspNetUsers` rows with password hashes plus the `Description`/`ClinicSignature` LOBs for every row). Single-lead reads follow suit (2026-09-15): the detail screen and every mutation response read `LeadDetailRow`/`LeadHistoryRow`/`LeadCallRow` projections, mutations load the tracked `Lead` with no Includes (only the admin edit asks for the Doctor/Procedure/Referal lookups, to describe what changed), and the per-doctor export projects `DoctorLeadRow`. `GET /api/Lead` (calendar) takes optional `from`/`to`, matched on each lead's latest call date; without them it still returns every lead that has a call. Users are read as `UserSummaryRow` (roles joined in, one query) — never `UserManager.GetRolesAsync` per user. The monthly questionnaire report loads all questionnaires' questions and split this-month/before rating counts once (`GetQuestionsAsync`, `GetRatingCountsSplitAsync`) and builds stats with `QuestionnaireService.BuildStats`. `GetQueueCountsAsync` is one `GroupBy(l => 1)` conditional-count query, not five `CountAsync` calls. `GetDashboardKpisAsync` runs two per-day bucket queries and sums in memory, not three queries per tile. Admin-dashboard aggregates (`kpis`, `status-counts`, `sources`, `employee-cases`, `stats`) are cached in `IMemoryCache` by `LeadService.CachedAsync` (60s TTL) and dropped by `InvalidateStats()` on every lead write — `ReloadActionResponse` is the single choke point every mutation flow passes through, plus `CreateLeadAsync`/`DeleteLeadAsync`; a new mutation path must reach one of those. Per-user data (`queue-counts`, `paged`) is deliberately not cached. `Leads` has indexes on `(Status, CreatedDate)` and `CreatedDate`, and `Name`/`NickName`/`PhoneNum`/`CountryKey` have max lengths (200/100/32/10) so they aren't LOBs. The Api csproj forces Workstation, non-concurrent GC for the 1 GB pool. `deploy.yml` must stay a RID-less framework-dependent publish launched via `dotnet <dll>` — a `-r win-x64` ReadyToRun publish (tried 2026-09-05) switches web.config to the `.exe` apphost and the host answered 500.30. Cold starts are handled by the frontend's 5-minute keep-alive ping instead.

**Deleted leads / recycle bin (added 2026-09-14, Admin only):** `DELETE /api/Lead/{id}` (optional body `{reason}`) never removes the row — it sets `Lead.IsDeleted`, adds a `DeletedLeads` row (`DeletedById`, `DeletedAt`, `Reason`) and a `Deleted` timeline entry. `GET /api/Lead/deleted?page&pageSize&search`, `GET /api/Lead/deleted/{id}` (full detail + who deleted it) and `POST /api/Lead/deleted/{id}/restore` (removes the `DeletedLeads` row, adds a `Restored` timeline entry that snapshots who deleted it and why). A global query filter `HasQueryFilter(l => !l.IsDeleted)` hides deleted leads from every `Leads` query; only the recycle-bin methods in `LeadRepo` use `IgnoreQueryFilters()`. The filter does **not** reach queries rooted at `LeadHistories`/`LeadCalls` — any new aggregate across leads over those tables must exclude `h.Lead.IsDeleted` itself, as `LeadHistoryRepo.SucceededInRange` does. EF logs warning 10622 about this on startup; it's expected. `LeadActions` is stored as int — `Deleted`/`Restored` were appended, never reorder.

`LeadStatsController` (`Area/CRM/Controllers`) has three actions with different access: `GET stats` (all-time `AdminStatsDTO`, Admin-only), `GET kpis` (`DashboardKpiDTO` — leads/successes this month vs today, each with a 7-day trend and a delta vs. the prior period, any CRM role), `GET employee-cases?period=today|month` (per-employee created-lead counts, any CRM role). `PaymentWays` intentionally stays `Cash`/`Insurance` only — those are the only two real payment methods.

### Feedback feature

Lives under `Area/Feedback/` in Api (`Area/Feedback/Controllers/`) and `DTOs/Feedback/` in Application. Ported from a separate legacy app (`D:/repos/CRMS/Feedback`), with these deliberate changes from that original:

- **No push/in-app notifications** — the old app pushed to a per-department head (in-app inbox + FCM web push + a SignalR hub). None of it came across, and with it went the `HeadUserId` column that only existed to route those notifications. The only notification is an **email** (added 2026-09-13, see below), routed by role + department instead of a head column.
- **No parallel user or department tables** — the old app owned its own `FeedbackUser` (with `CanView`/`CanViewAll`/`CanManage`/`CanManageLists` flags) and its own bilingual `Department`. Both are gone: staff are the normal Identity `User`, and `PatientFeedback.DepartmentId` points at the shared `Departments` lookup that `User.DepartmentId` already pointed at, which is what makes department scoping a plain column comparison.
- **Capabilities became roles** — ported as an `FManager/FEmployee/FUser` tier alongside CRM's `C*`, **collapsed to `FManager` alone on 2026-09-20**. The old `view`/`manage` split (FEmployee = own department, may act; FUser = own department, read-only) was never used here — neither role was ever granted, in dev or prod, so both were deleted from `AppRoles`, the seed list and the DB. Running a department's inbox is one job: `FManager` reads and works the departments on their token, Admin every department (the old `feedback.viewAll`). `FeedbackController` keeps `FeedbackAccess`/`CanWork`/`CanReport` as three separate constants although all three now hold the same pair — they answer three different questions, and a role added back to one must not silently widen the other two. The old `feedback.lists` key is just Admin on the existing `DepartmentController`.
- **Names via navigation, not snapshots** — the old app snapshotted `ActorUsername`/`AssignedToUsername` because it never saw the Auth DB. Here `AssignedToId`/`FeedbackHistory.ActorId` are real `AspNetUsers` FKs read through EF navigation, same as `Lead.ClaimedById`. The two department names on a `Forwarded` timeline entry stay snapshots on purpose — renaming a department later must not rewrite what the timeline says happened.

`PatientFeedback` is named that way (not `Feedback`) so it doesn't collide with the `...Models.Feedback` namespace. `FeedbackHistory` is the append-only timeline (`StatusChanged`, `Assigned`, `Unassigned`, `Note`, `Forwarded`), mirroring `LeadHistory`. `CreatedDate` is `AppClock.Now` (Jordan), matching `Lead.CreatedDate` — don't mix UTC in.

**Visibility is the whole security model here** and it lives in `FeedbackService.VisibleDepartments`/`CanSee`: only an Admin is unrestricted — everyone else, FManager included, is narrowed to the departments on their own token (a manager normally runs one department's feedback, and the dashboard they get is that department's numbers), and a message outside that set answers **404, not 403** — not confirming that an id exists is the point of the scoping. The department ids come from the signed token (`AppClaims.DepartmentId`, added to `TokenService` 2026-09-09; `AppClaims.DepartmentIds` 2026-09-19, see **Multi-department users** below) and never from the request body; a change to a user's departments takes effect on the next refresh, same as a role change. `FeedbackListQuery.RestrictToDepartmentIds`/`FeedbackStatsQuery.RestrictToDepartmentIds` are set by the service, never by the caller — `null` there means unrestricted (Admin), and an **empty list means nothing at all**, which is why the repos branch on it explicitly instead of skipping the filter.

`GET /api/Feedback/stats` (`CanReport` = Admin + FManager) is the dashboard behind that scoping: status and type counts, average time from arrival to `ResolvedAt`, the age of the oldest still-open message, a per-resolver breakdown read from the timeline (`StatusChanged` -> `Resolved`, so it credits who actually closed it rather than who it was assigned to), and a per-department breakdown that only an admin ever sees more than one row of. It is aggregated in SQL in `PatientFeedbackRepo.GetStatsAsync` — six grouped queries, no message rows — and every count is over the messages *received* in the period, so one date meaning runs through the whole screen.

`PublicFeedbackController` (`api/public/feedback`) is the only anonymous surface besides login — submit, plus the active-department list its dropdown needs. It is a separate controller from `FeedbackController` specifically so `[AllowAnonymous]` can never leak onto a read endpoint, and it runs under its own tighter `"PublicFormLimit"` rate-limit policy (10/min per IP) rather than sharing the general anonymous allowance with login attempts. A submit returns the reference number and nothing else — never the stored record.

Reference numbers are `AMH-XXXXXX` over an alphabet with `I/O/0/1` removed (patients read these off a phone and repeat them out loud); `IReferenceNumberGenerator` is a singleton, and `FeedbackService` retries on collision. Phone numbers are stored digits-only with the national leading zero stripped and the country code in its own column, so inbox search is leading-zero-tolerant the same way lead search is. The inbox list projects into `Domain/IRepositories/Feedback/FeedbackListRow` (never `Include`s the assignee's `AspNetUsers` row or the `Details` column for a list), and `Feedbacks` has indexes on `(DepartmentId, CreatedDate)`, `(Status, CreatedDate)` and a unique `ReferenceNumber` — same reasoning as the CRM performance shape above. Unlike the CRM list endpoints, feedback does **not** use `IFilterCacheService`; add it if the frontend wants last-filter restore.

**New-feedback email (2026-09-13):** after a public submit is saved, `FeedbackService.NotifyDepartmentManagersAsync` emails every active `FManager` whose `DepartmentId` matches the message and whose Identity `Email` is set (`IUserRepo.GetActiveEmailsInRoleAsync`, one join query) — one message per recipient, Arabic RTL body from `FeedbackEmailTemplate`, patient fields HTML-encoded, with an "open message" button to `{Email:ConsoleBaseUrl}/fb/inbox/{id}` (the console's login round-trips `?next=` back to it; blank config drops the button). Admins are not included. Best-effort: nothing in it may fail the submit. `IEmailQueue` (Application) → `Api/Email/ChannelEmailQueue` (bounded in-memory channel, singleton) → `SmtpEmailBackgroundService` (a hosted service in the web process, MailKit, 3 attempts, no retry on auth/5xx). Queued mail is lost on an app-pool recycle — accepted, the message is already in the inbox. SMTP config is the `Email` section (Hostinger: `smtp.hostinger.com`, 465 = SSL-on-connect, anything else = STARTTLS); `Username`/`Password`/`FromAddress` are blank in the tracked file and injected by `deploy.yml` from `PROD_SMTP_USERNAME`/`PROD_SMTP_PASSWORD` — if they're missing the app starts fine and logs that email is disabled. User create/update DTOs carry an optional `Email` (blank = none, validated in `UserServices.TryNormalizeEmail`; update is a full replace, so omitting it clears it).

### Questionnaires feature (added 2026-09-13)

Patient satisfaction questionnaires. Lives under `Area/Questionnaires/` in Api, `DTOs/Questionnaires/` in Application, `Models/Questionnaires/` in Domain (plural namespace so `Questionnaire` doesn't collide with it). `Questionnaire` (title, unique `Slug`, `DepartmentId`, `IsActive`) → `QuestionnaireQuestion` (`DisplayOrder`, `IsArchived`) → `QuestionnaireSubmission` (anonymous, IP/UA audit, local `CreatedDate`) → `QuestionnaireAnswer` (`QuestionRating` enum `VeryBad=1 … VeryGood=5` — the numeric values are the score, averages are taken over them, don't renumber).

- **Access**: `QuestionnaireController` is `Admin` + `QManager` (role added 2026-09-13, seeded). Scoping is the feedback rule exactly: Admin sees every department, a QManager only `AppClaims.DepartmentId` from their token, and anything outside answers **404**. A QManager's create/update always lands in their own department whatever `DepartmentId` they send.
- **Editing**: update is a full replace of the question list. A sent id must be one of this questionnaire's live questions (else 409); a question left out is **archived** if it has answers (results keep showing it, last, marked) and deleted otherwise. Delete of a whole questionnaire is refused once it has submissions — deactivate instead. `QuestionnaireAnswer → Question` is `Restrict` because the questionnaire already cascades to answers through submissions (SQL Server rejects two cascade paths).
- **Public**: `PublicQuestionnaireController` (`api/public/questionnaire/{slug}`, `[AllowAnonymous]`, `PublicFormLimit`) — GET title+questions, POST `{answers:[{questionId,rating}]}`; every live question must be answered exactly once. Optional `name` (≤100) and `phoneNumber` (7-15 digits once separators are stripped, stored digits-only with a leading `+` kept — no country picker, so no national-zero stripping) ride on the same submission; `GET {id}/submissions?page&pageSize&contactOnly` lists responses newest-first with them and each response's own average. The page itself is the static site in `D:\AmalQuestionnaire` (`survey.alamalhospitaljo.com/{slug}`, in `Cors:AllowedOrigins`).
- **Excel + charts (2026-09-13)**: `GET {id}/export` (Summary / By Question / Trend / Responses) and `GET export` (overview). ClosedXML has no chart API, so `ExcelChartWriter` post-processes the saved workbook with the Open XML SDK (ClosedXML's own dependency) and adds **native Excel charts bound to the cells** — which is why Average/Satisfied cells are real numbers (Satisfied as a fraction with `0.0%`), blank when null (a gap, not a zero). `<drawing>` must be inserted at its schema position in the worksheet or Excel "repairs" the file and drops the charts; verified by opening the output in desktop Excel via COM and exporting each chart to PNG. `QuestionnaireTrendBuilder` (12-month window ending at the period's last month, plus "that month vs every month before") feeds both the Trend sheet and the monthly email so they can't disagree.
- **Monthly QManager email (2026-09-13)**: `QuestionnaireMonthlyReportScheduler` (hosted service in Api, wakes every 30 min, `QuestionnaireReport:Enabled/SendDay/SendHour`, default day 1 after 08:00 local) sends *last* month's report: one email per department to every active `QManager` with an email (`IUserRepo.GetActiveEmailsInRoleAsync`), Arabic RTL, table-cell bar "charts" (not images — mail clients block them), each questionnaire's workbook attached (`EmailMessage.Attachments`). Once-per-month is the `QuestionnaireReportRuns` row with a unique (Year, Month), claimed only after the report is built and only when `IEmailQueue.IsEnabled` — so a restart, a missed hour or a second worker just catches up, never double-sends. Admin-only: `GET monthly-report/preview?year&month&departmentId` (the email as HTML, with To/attachments), `GET {id}/monthly-report/attachment`, `POST monthly-report/send` (manual resend, ignores the log).
- Stats (`GET {id}/stats`, and the list's per-row numbers) are aggregated in SQL (`QuestionnaireRepo` — grouped counts per question × rating, no answer rows). "Satisfaction" = share of answers rated Good/VeryGood; averages/percents are `null`, never 0, when nothing was answered.

### Appointments feature (added 2026-09-15, moved onto departments 2026-09-16)

Anonymous appointment requests from the static page in `D:\AmalAppointment` (`appointment.alamalhospitaljo.com`, in `Cors:AllowedOrigins`; built from the feedback page, full-window split layout from 960px), plus the booking team's inbox for them. Lives under `Area/Appointments/` in Api, `DTOs/Appointments/` in Application, `Models/Appointments/` in Domain.

**The whole feature is the feedback feature with different nouns**, deliberately: `AppointmentRequest` mirrors `PatientFeedback`, `AppointmentHistory` mirrors `FeedbackHistory`, `AppointmentController` mirrors `FeedbackController`, and `AppointmentService.VisibleDepartment`/`CanSee` are `FeedbackService`'s rules verbatim — only an Admin is unrestricted, everyone else (AManager included) is narrowed to `AppClaims.DepartmentId` from their own token, and anything outside it answers **404, not 403**. Read the Feedback section above for the reasoning behind any of it.

- `AppointmentRequest` — full name, country code + national number stored like feedback (digits only, leading zero stripped), `DepartmentId`, `ReferralSourceId`, optional details, IP/UA audit, `AppClock.Now`, plus the workflow: `Status`, `AssignedToId`, `CompletedAt`.
- **`DepartmentId` is the routing decision** and replaced an appointment-only `AppointmentProcedures` list on 2026-09-16. A procedure said nothing about who owned the request, so the notification had to be aimed at a hand-maintained `AppointmentNotificationEmails` table; both tables are gone. The department is the shared `Departments` lookup — the same one `User.DepartmentId` and `PatientFeedback.DepartmentId` point at — so scoping is a plain column comparison and the email has a role to aim at.
- `AppointmentStatus` is `New, Contacted, Scheduled, Cancelled`. **`Scheduled` is the success terminal** (the request became a real appointment) and the only status that stamps `CompletedAt`; leaving it clears the stamp, so "time to book" never averages over a stamp that no longer describes the row. Stored as int — append, never reorder, same for `AppointmentActions` (`StatusChanged, Assigned, Unassigned, Note, Forwarded`).
- **Roles**: `AManager` alone, seeded by `DbInitializer`. It shipped as an `AManager/AEmployee/AUser` tier copied from `F*`, and lost its bottom two on 2026-09-20 with feedback's — same reason, same day, neither ever granted. `AppointmentController`'s `AppointmentAccess`/`CanWork`/`CanReport` are all AManager + Admin now, kept as three names for the reason `FeedbackController` gives.
- **Email**: after a public submit, `AppointmentService.NotifyDepartmentManagersAsync` emails every active `AManager` of the request's department who has an Identity `Email` (`IUserRepo.GetActiveEmailsInRoleAsync`, the same call feedback makes), Arabic RTL from `AppointmentEmailTemplate`, patient fields HTML-encoded, a `tel:` link on the phone and an "open request" button to `{Email:ConsoleBaseUrl}/ap/inbox/{id}`. Best-effort through `IEmailQueue`; nothing in it may fail the patient's submit.
- It keeps **its own** referral-sources list (`AppointmentReferralSources`, unique name, retired with `IsActive`, FK `Restrict`), deliberately not the CRM's `Referals` — the two are maintained by different people for different audiences. Admin-only `AppointmentListsController` (`api/AppointmentLists/referral-sources` GET/POST, `PUT …/{id}`), answering the saved row or `{message}` 400/404. Console: Settings → Appointments.
- `PublicAppointmentController` (`api/public/appointment`, `[AllowAnonymous]`, `PublicFormLimit`): `GET options` returns the active departments (in `DisplayOrder`) and referral sources in one call, `POST` submits; inactive or missing ids are rejected in Arabic. A submit answers `{success, createdDate}` — never the stored record.
- **Performance shape** follows the feedback one: the inbox projects into `AppointmentListRow` (`AppointmentRequestRepo.ToRow`, no `Include`, no `Details`), the dashboard is six grouped SQL queries in `GetStatsAsync` returning no request rows, and `AppointmentRequests` has indexes on `(DepartmentId, CreatedDate)`, `(Status, CreatedDate)` and `CreatedDate` with bounded lengths on the searched columns. Bookers are credited from the **timeline** (`StatusChanged -> Scheduled`), not from `AssignedToId`: whoever picked it up is not always whoever booked it. There is no Excel export on this dashboard yet — the one thing feedback's has that this doesn't.

### Tickets feature (added 2026-09-17, reshaped 2026-09-19)

Staff support tickets, ported from the CRMS Tickets app (`D:\repos\CRMS\Tickets`). Lives under `Area/Tickets/` in Api, `DTOs/Tickets/` in Application, `Models/Tickets/` in Domain. Built in the Appointments shape (actor record from the controller, projected rows, timeline saved with every change, 404 for what the caller may not read, 409 `{message}` for a broken rule).

**The 2026-09-19 reshape split raising from solving**, and made the raising roles department-scoped where they were not before. Nothing had shipped — prod had zero tickets and zero `T*` grants — so the model was changed in place rather than migrated around. `Ticket.DepartmentId` is still the creator's department at the moment they raised it (from their token; null when none), but it is now load-bearing: it is what a `TManager`'s view filters on.

- **Reading and solving are different rules.** `TicketService.CanSee` is the wider one: an Admin reads everything; a creator always follows their own ticket; a **flagged** ticket is the insurance desk's alone; otherwise the support agent reads every department's and a `TManager` reads their own department's. `TicketService.Works` is the narrower one and decides who may close or reopen — the insurance desk for a flagged ticket, the support agent for everything else. **Neither raising role solves anything**, however much of their department they can read.
- **`PaymentMethod` is gone; `Ticket.IsInsurance` (bool) replaced it** on 2026-09-19. Cash vs Insurance was never a payment fact here — it was a routing flag whose other half meant nothing, so it was noise on every form. The flag may only be set on a procedure whose **`TicketProcedure.AllowsInsurance`** is true (seeded: "فتح فاتورة"), and `CreateAsync` answers 409 anywhere else rather than silently dropping it — a raiser who believed their ticket was going to the insurance desk must not find it in the support queue instead. The rule reads that column rather than comparing names, so renaming the procedure can't break the routing; `TicketProcedureItemDTO.AllowsInsurance` is deliberately `bool?` so an admin editing the name and omitting the flag doesn't switch the desk off.
- **Roles**: `TEmployee` raises tickets and follows only their own (`created-by-me`, and a queue holding the same); `TManager` raises too and reads every ticket raised inside their own department; **`TSupport`** (added 2026-09-19) is the support agent — the one not-per-department ticket role — and receives and solves everything not flagged insurance; `TInsurance` owns the flagged ones and raises none. `TUser` was removed the same day: `TEmployee` is now what it was. Controller policies: `CanCreate` = TManager/TEmployee/Admin, `CanWork` (close **and** reopen — reopening is a correction to a close, so it belongs to the same desk rather than a seniority tier) = TSupport/TInsurance/Admin, `CanReport` = Admin. The queue endpoint has no gate beyond the class one, because a TEmployee's queue is simply their own tickets.
- **Three procedures are seeded**, not left to an admin to type (`DbInitializer.SeedTicketProceduresAsync`, run beside the role seeding on every cold start): حذف (delete), خصم (discount), فتح فاتورة (open invoice) — the last with `AllowsInsurance`, so the insurance desk can receive anything at all. Matched by name and only ever inserted, never updated or removed, so a later rename or retirement isn't undone on the next restart.
- **Workflow**: `TicketStatus` is `Open, Success, Failed`; closing picks one and `Failed` requires a reason (`Resolution`). No claim step: the closer becomes `AssignedToId`. Closing stamps `ClosedAt`; reopening clears `ClosedAt` and `Resolution` (the original kept them). A closed ticket is locked except for reopen. A creator may comment on their own open ticket but not close it. `TicketStatus`/`TicketActions`/`TicketType` are stored as int — append, never reorder.
- **Emails replace the old in-app bell** (and its `KnownUser` cache), through `IEmailQueue`, Arabic RTL from `TicketEmailTemplate`, linking `{Email:ConsoleBaseUrl}/tk/tickets/{id}`, best-effort, never mailing the actor: a new ticket -> active `TSupport`, or `TInsurance` for a flagged one; closed -> the creator. The department roles are **not** mailed per ticket — a manager reads their department's queue rather than being told about each one. Admins are not mailed. Recipients come from `IUserRepo.GetActiveEmailsInRolesAsync` (no department) / `GetActiveEmailAsync`.
- **Lists**: the ticket app's own `TicketCategories` and `TicketProcedures`, deliberately not the CRM's `Procedures`. Admin-only `TicketListsController` (`api/TicketLists/{categories|procedures}` GET/POST, `PUT …/{id}`); raisers read active entries in one call from `GET api/Ticket/options`. **The reason is free text** (`Ticket.Reason`, nvarchar(2000), several lines, detail-only — not in list rows): a per-procedure `TicketReasons` list was removed on 2026-09-19 (migration `TicketReasonAsFreeText` copies each picked reason's name into the new column before dropping the table and `ReasonId`).
- **Endpoints** (`api/Ticket`): `paged?scope=Open|Mine|Unassigned|Closed&status&categoryId&search` (the queue; an explicit status wins over the scope's own rule; Closed sorts by `ClosedAt`), `created-by-me`, `{id}`, `stats`, and POST `{id}/comments|close|reopen`. The queue's visibility arms **OR** together in `TicketRepo.PageTicketsAsync` (own tickets, plus the support queue, plus the flagged ones, plus a department), so holding two roles widens it rather than narrowing it; Admin short-circuits the lot. Indexes follow: `(IsInsurance, Status, CreatedDate)` and `(DepartmentId, CreatedDate)` replaced the old payment-method one.
- **Dashboard** (`GET stats?from&to`, Admin-only, added 2026-09-19): status split, insurance share, average **first reply** and **time to close**, the age of the longest-waiting open ticket, and per-person figures, plus breakdowns by department, procedure and category. Six grouped queries in `TicketRepo.GetStatsAsync` returning no ticket rows, the feedback/appointment shape, plus one correlated first-row-per-ticket pass (OUTER APPLY) for who answered first — that one can't be grouped, since "first" needs an ordering. The period bounds when a ticket was **raised**, so one date meaning runs through every number. **Answering and closing are counted separately on purpose**: whoever replies first is often not whoever closes, and the creator's own entries never count as a response to themselves. Averages are `null`, never 0, when there is nothing to average. List rows project into `TicketListRow`, the detail into `TicketDetailRow`, no `Include`. `SourceUrl` is accepted only as an http(s) URL since the console links it. `Type`/`PatientId`/`SourceUrl` are filled by the CertaCure browser extension (`C:\Users\it.officer\Desktop\certacure-extension`, not in this repo; v4.0, 2026-09-19), which rides the console session through the console's `/api/tickets` and `/api/tickets/options` proxies (renewing via the console's `/api/auth/refresh`, never the API's, so it never double-spends a refresh token), and on a procedure with `AllowsInsurance` sets `IsInsurance` from the invoice's "Parent Payer" field (any value = insurance, empty or missing = not) instead of a checkbox.
- Nothing was imported from the old Tickets database.

### Multi-department users (added 2026-09-19)

One person overseeing several departments — reading all of their feedback, appointment requests and questionnaires, and being emailed about all of them — without being made an Admin. `UserDepartments` (`UserId` + `DepartmentId`, composite PK, cascade from `AspNetUsers`, `Restrict` on `Departments`) is the only new table.

**`User.DepartmentId` stays, and is a different fact from the grants.** It is the department the person *works in*: the floor of what they can read, and what every write that records a department stamps — `TicketService`'s originating department, and where a QManager's new questionnaire lands. The grant rows only widen *reading*. The effective reach is always the **union** of the two, so a grant can never cost someone their own department, and a user with no rows behaves exactly as every account did before the table existed.

- **The token carries the resolved set**, not the table: `AppClaims.DepartmentIds` (`"department_ids"`, comma-separated) is built in `TokenService` from the home department plus `IAuthRepo.GetExtraDepartmentIdsAsync`, at the one choke point login and refresh share (`AuthService.IssueAsync`). No request ever joins through `UserDepartments`. A token issued before the claim existed simply lacks it, and `AppClaims.ReadableDepartmentIds` falls back to the home department alone — old sessions degrade to the old behavior rather than breaking, until their next refresh (<= 15 min, same as a role change).
- **All three department-scoped areas changed together** and identically, because their rules were already verbatim copies: `FeedbackService`/`AppointmentService`/`QuestionnaireService` each expose `VisibleDepartments` (null = Admin, otherwise the set) and a `CanSee` that does `Contains`. The actors carry both `DepartmentId` and `DepartmentIds`. CRM and Tickets are not department-scoped and were untouched.
- **`null` vs empty is load-bearing.** `null` restriction means unrestricted and is Admin only; an empty set means the caller may read *nothing*. `PatientFeedbackRepo`, `AppointmentRequestRepo` and `QuestionnaireRepo` each branch on this explicitly (`readable.Count == 0 ? Where(x => false) : Where(x => readable.Contains(...))`) rather than skipping the filter — treating empty as "no restriction" would hand a department-less account the whole hospital.
- **Email follows reading**: `IUserRepo.GetActiveEmailsInRoleAsync(role, departmentId)` now matches `u.DepartmentId == d || u.ExtraDepartments.Any(...)`, still one join. Whoever can read a message is whoever hears about it. A user granted three departments gets three monthly questionnaire report emails, one per department — that is the per-department report working correctly, not a duplicate.
- **A QManager may now create in any department they can read** (`ResolveDepartmentAsync`), defaulting to their home one, because seeing three departments' results while only ever being able to create in one is half a feature. Anything outside the grant is still refused.
- **Admin surface**: `CreateUserDTO`/`UpdateUserDto`/`GetUserResponse` carry `ExtraDepartmentIds`; update is a **full replace** (like `Email`), the home id is dropped if sent, and an id that doesn't exist is refused rather than silently ignored. Console: Settings → Users, an "Also sees" checkbox list on the user form, and the department cell reads "Radiology +2".
- **Console gating is no longer role-only**: `seesManyDepartments`/`pickableDepartments` (`src/lib/nav.ts`) offer the department filter to an Admin *or* anyone whose token holds more than one department, and list only the departments that person can actually read. The dashboards' By department tables were already data-driven (`departments.length > 1`), so they followed with no change.

### Filter persistence (no Redis — see hosting note below)

List endpoints that take filter/paging query params (`LeadController.GetPaged`/`GetCreatedByMePaged`, `HospitalManagerController.GetStats`/`ExportStats`) remember each user's last-used filter via `IFilterCacheService` (`Application/Services/Interface`), so a bare request with **no query string** restores it instead of falling back to hard defaults — any query string present is used exactly as sent and becomes the new saved value. Cache key is `filter:{userId}:{endpointKey}`.

This is backed by `IDistributedCache` (`AddDistributedMemoryCache()` in `Program.cs`, in-process only) rather than Redis — the production host is **smartasp.net shared hosting**, which can't run Redis or any other separately-hosted service. `IFilterCacheRepo` (Domain) → `FilterCacheRepo` (Infrastructure, wraps `IDistributedCache`) is the only place that would need to change to move to Redis later (`AddStackExchangeRedisCache(...)` instead of `AddDistributedMemoryCache()`); everything above that talks only to the abstraction. TTL is `FilterCacheSettings:TtlDays` in config (default 30). Keep this constraint in mind before adding any other infra that needs its own running process.

### Auth & authorization

JWT bearer (`Microsoft.AspNetCore.Authentication.JwtBearer`) + ASP.NET Identity (`User : IdentityUser`, `IdentityRole`). Roles are fixed strings in `AlAmalBusiness.Domain.Constants.AppRoles`: `Admin`, the per-department CRM tier `CManager/CEmployee/CUser`, the single per-department roles `FManager` (Feedback) and `AManager` (Appointments, added 2026-09-16) — each shipped as a three-tier copy of `C*` and was cut back to its manager on 2026-09-20, since `FEmployee`/`FUser`/`AEmployee`/`AUser` were never granted to anyone and the role rows are gone from both databases — plus the ticket roles `TManager/TEmployee/TSupport/TInsurance` (added 2026-09-17, reshaped 2026-09-19 — `TManager`/`TEmployee` raise and are department-scoped, `TSupport`/`TInsurance` solve and are not; see Tickets). (The F* tier was labelled "Finance" here until 2026-09-10; it is the feedback site's, and a parallel `FBManager/FBEmployee/FBUser` trio briefly added for `FeedbackController` was a second spelling of the same three and has been removed.) `DbInitializer.SeedRolesAsync` seeds these on startup.

Authorization is **secure-by-default**: `Program.cs` sets a global `FallbackPolicy` requiring an authenticated user, so any new endpoint needs an explicit `[Authorize]`/`[AllowAnonymous]` — nothing is anonymous by omission. `AuthController.Login` is the one `[AllowAnonymous]` endpoint. `UserController` and `DepartmentController`'s admin-only actions are role-gated via `[Authorize(Roles = nameof(AppRoles.X))]`. `GET /api/Auth/me` returns the caller's own `GetUserResponse` (id/username/fullname/roles) — covered by the fallback policy, no explicit attribute. The JWT itself carries `sub`, `unique_name`, `name` (= `FullName`, added 2026-09-05), `department_id` (= `AppClaims.DepartmentId`, added 2026-09-09 — the feedback inbox scopes on it, so it is an authorization input, not decoration) and `role` claims, and the Next.js console reads the current user from those claims instead of calling `/me` on every page — keep `name` in the token (`TokenService`) or the console's header/role gates lose the display name.

**Sessions (added 2026-09-05):** the access token stays 15 minutes, and a `RefreshToken` row (Domain/Models, hashed with SHA-256 — the raw value only ever lives in the client's cookie) keeps a session alive for `JwtSettings:RefreshDays` (7). `POST /api/Auth/refresh` rotates: the presented token is spent and replaced, and presenting an already-spent one revokes every live token for that user, on the assumption it leaked. Refresh re-reads the user and their roles, so disabling an account or changing its roles takes effect within 15 minutes instead of lasting as long as a browser stays open. `POST /api/Auth/logout` revokes one session and always returns 200. Spent rows are swept inside `AuthService.IssueAsync` because this host runs no scheduled jobs — `SweepAsync` is time-gated (once an hour per process, `JwtSettings:SweepEveryMinutes`) rather than the 1-in-50 roll it started as, and `IRefreshTokenRepo.DeleteSpentAsync` drops a row as soon as it is **expired** (refresh refuses those anyway) or has been **revoked** longer than `JwtSettings:RevokedRetentionHours` (48). Rotation, not sign-in, is what fills this table — every refresh spends one row and writes another — so the old sweep, which fired rarely and only cleared rows a week *past* expiry, never kept up: prod reached 595 rows for 15 usable sessions (2026-09-19, cleaned to 79 with the same predicate). A revoked row is kept only so a replayed token trips the leak check, which is worth nothing once no client could still hold the value; a live row matches neither arm and is never touched. `/api/Auth/login` returns JSON (`token`, `refreshToken`, `expiresInSeconds`, `refreshExpiresInSeconds`), not the bare string it used to.

`AppDbContext.OnModelCreating` must call `base.OnModelCreating(modelBuilder)` first — without it, Identity's own entity configuration (including .NET 10's Passkey entities) silently isn't applied, which breaks `dotnet ef migrations add` entirely with an opaque "requires a primary key" error.

Rate limiting is two-layer, configured in `Program.cs`: a global per-IP sliding-window safety net (`GlobalLimiter`), plus a `"PerUserLimit"` policy (tighter per-authenticated-user limit, looser per-anonymous-IP limit) that controllers opt into via `[EnableRateLimiting("PerUserLimit")]`. `RateLimiterSettings:WhitelistedIps` in config bypasses both layers.

**Forwarded client IP (2026-09-15):** every limiter and the whitelist key on `RemoteIpAddress`, which `UseForwardedHeaders` takes from `X-Forwarded-For`. The console's Next server proxies staff traffic and has no fixed address, so the proxy is trusted by a shared secret, not by IP: a middleware in `Program.cs` strips `X-Forwarded-*` from any request whose `X-Proxy-Secret` doesn't equal `ForwardedHeaders:ProxySecret` (32+ chars; injected by `deploy.yml` from `PROD_PROXY_SECRET`; the console sends it from its `API_PROXY_SECRET` env, `src/lib/forwarded-headers.ts`). Before this any client could send `X-Forwarded-For: <office IP>` and skip every limit. With the secret unset, forwarded headers are ignored and all console traffic shares the console server's IP bucket. Request bodies are capped at 4 MB (`MaxRequestBodyBytes`); an oversized body answers 413 via the `/error` handler.

**Lockout (2026-09-15):** 5 wrong passwords lock an account for 15 minutes (Identity `Lockout` options). `AuthRepo.LogInAsync` reads `LockoutEnd` itself instead of `IsLockedOutAsync`, because CRMS-imported accounts may have `LockoutEnabled = false`. An admin password reset or enable clears the lockout; a password reset or disable also revokes the user's refresh tokens (`UserServices`).

SignalR hub auth: browsers can't set an `Authorization` header on a WebSocket handshake, so the JWT bearer's `OnMessageReceived` event reads the token from `?access_token=` on requests under `/hubs` (see `Program.cs`) — needed for any future hub, not just `LeadHub`.
